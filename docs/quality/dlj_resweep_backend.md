## 2. Fix interactions and isolation

The shipping tree has one imperative schema upgrade, not four independent revision scripts. Its BE1 event fields and BE2 timestamp conversions compose. The more consequential interactions are between billing and retention, and between BE3 validation and the UI.

- **DDL order.** `db/models.py:104–138` adds two ApiKey columns, a nullable unique customer index and a separate receipt table. BE3 changes request validation and uses existing category/revision columns. It adds no competing LabelLog or ApiKey column. On an existing database, `db/migrate.py:118–155` renames eligible provider columns, adds or repairs timestamps, adds the event ID, creates indexes, then creates missing tables from ORM metadata. On an empty database metadata creates the final shape directly. Reapplying the *combined* migration is supported. Running new workers against the old schema is unsafe, and concurrent migration processes are not serialized by the inspector checks. Run the migration once before worker rollout.
- **Imports and errors.** The mounted modules at `jm_service.py:40–52,283–292` import cleanly in the test runs. The connector imports IngestItem from the labeling router. Billing imports the auth session dependency and validates raw event dictionaries, so it shares no BE3 Pydantic request model. Tightened validation does affect connector adapters and frontend category choices. The browser's HTTP status and text parsing is improved, with remaining gaps at R17.
- **Fixtures.** `test_tasks.py:21–70` builds a private SQLite file or a random PostgreSQL schema per case. Billing and validation reuse that helper and independently monkeypatch the factory or connector path/environment. `test_migration_fixes.py:25–57` creates a separate schema/file, overrides the migration engine and cleans it up. Fixed synthetic IDs are local to those stores. `test_billing.py:91,163,216` and `test_account.py:26` explicitly create SQLite engines even in a PostgreSQL-configured run. Monkeypatch restores module globals on teardown. Two module orders were exercised; this is evidence for those orders, not proof of unrestricted concurrent execution in one interpreter.

### Reservation and transaction boundaries

There is no shared `get_key` that checks entitlements. The path is `auth.py:81–95` → tenant/key hash in the same session → endpoint → `trial_guard.py:62–102` where applicable. PostgreSQL locks the active key row, resets stale UTC day/month buckets, checks expiry and the cap **before** incrementing. Trial is 14 days and 50/day with no lifetime cap. Paid monthly limits are 10,000 / 100,000 / 1,000,000 for starter/professional/business; scale and enterprise are unlimited. A used count of cap−1 admits one, cap admits zero. At precisely the trial expiry timestamp the code uses strict greater-than. Both counters remain on upgrade and a subsequent request uses the paid monthly policy. The billing module's duplicate cap dictionary does not drive enforcement.

The request-scoped session commits on success and rolls back on exception (`db/connection.py:55–62`). A later over-cap item in atomic ingest/batch or sample rolls back prior scores and reservations. Bulk prechecks membership before writes, skips verified/unscored/stale rows without charging, processes eligible rows until a quota 429, and returns per-row reasons for the rest. Expiry 402, a stale-engine conflict or another error aborts the transaction, including the earlier successes. At cap with three eligible rows it reports 0 processed and 3 skipped. Separate HTTP upload chunks commit independently. PostgreSQL concurrent reservations wait on the same key; SQLite locking differences are covered by R24. The independent legacy API has request limits on selected endpoints but no connection to these billing counters.

### Entitlement transitions

Signup creates an active trial (auth.py:49–66). Checkout sends tenant and purchasing-key UUID but does not itself upgrade the account (billing.py:59–93). A valid creation sets the customer, subscription and tier. Updates match only the stored subscription ID and update the tier if a product is present. Active status can clear cancellation only after the stored timestamp. Canceled sets the occurrence time and retains the paid tier and active flag. A newer active update or creation can clear cancellation before cleanup. At 30 days the hourly scheduler can remove tenant data and disable the key. A sibling key can defer deletion. There is no automatic restoration of deleted data.

Each accepted handled event inserts its ID into the receipt table in the entitlement transaction. Its primary key is the deduplication index; `api_keys.paddle_event_id` is the last-applied marker and needs no replay lookup index. A stale event keeps its receipt but does not change the watermark. A rolled-back business failure also rolls back its receipt. Duplicates receive 409 even if another event intervened. Other event types return success without a receipt. No notification freshness window is enforced by the signature check. The linked customer index is unique for non-NULL values, whereas subscription ID has neither a unique constraint nor a lookup index.

**Nulls, defaults and history.** Historical additions introduce no unexplained new production columns absent from the models. Temporary rebuild tables are dropped on success. Renamed predecessor-provider columns can coexist with empty new columns, especially on SQLite. ORM list defaults, UUID generation, engine versions and some tenant defaults are client-side; server defaults are not interchangeable. The rebuilt label PK lacks the ORM UUID default and explicit NOT NULL. On a fresh SQLite database the PostgreSQL-style gen_random_uuid() default also relies on an unavailable function unless supplied by the environment; ORM-inserted UUIDs normally mask it. Baseline columns existing before these additive migrations are assumed present. The migration is incremental rather than a general-purpose schema reconciler.

**Delete and write races.** Scheduler explicitly deletes LabelLog, Engine and Annotator before Domain. Child content cascades with LabelLog; predecessor/successor strings have no FK and an incomplete chain returns 409. PostgreSQL locks the current row through a relabel chain. Verify rejects a superseded row and already-verified rows. Two simultaneous scores for the same label converge on unique (domain_id,label_id); a rejected request rolls back its quota. Optimistic engine updates check the old version and affected-row count (db/repository.py:49–69). Bulk verifies lock the requested labels before training, protecting an overlapping successful verify on PostgreSQL. Neither globally ordered batch locks nor a common retry policy for deadlocks exists. SQLite has database writer serialization, not the PostgreSQL row-lock guarantee. Version checks protect engine state, not every label or read-modify-write quota counter.

**Dialect differences.** PostgreSQL's legacy time repair uses AT TIME ZONE 'UTC' on reflected DateTime without timezone; already-zoned columns are left alone. This is correct for the documented naive-UTC history and cannot infer another historical local zone. It does not validate or normalize future naive Python inputs. Writers use aware UTC, and read sites such as billing.py:212–216 and trial_guard.py:29–35 treat SQLite's naive return values as UTC. The model uses SQLAlchemy JSON, PostgreSQL JSON expansion versus SQLite json_each in dashboard_router.py:302–310, and dialect-specific annotator upserts in db/repository.py:179–194. Only PostgreSQL uses the sample advisory lock. Both backends bind search operands and escape literal wildcard characters. Unicode lower/collation behavior is database-dependent. PostgreSQL enforces VARCHAR widths and rejects embedded NUL in text; SQLite does not offer equivalent checks.

## 8. Regressions and remaining risks introduced or exposed by the fixes

The new receipt primary key and partial unique customer index give the critical billing identity checks indexed access. The fixes also brought behavioral changes that were not exercised by the legacy ops suite, including mandatory event metadata and the catalog check on a cancellation.

- **Cost.** The new per-verify domain configuration read happens inside bulk's existing loop, after the outer bulk handler has read the same schema. The full-history stats query and repeated engine/revision reads are older costs, not caused by the fixes. There is no evidence the receipt insert converted an indexed replay check into a scan. Subscription-ID lookups scan in the absence of a supporting index. Pending count and page reuse predicates but execute separate statements; under concurrent writes their snapshots can disagree on PostgreSQL READ COMMITTED. The list query materializes full text server-side before slicing its 80-character preview.
- **Validation and lifecycle.** Scored relabel uses the tenant-scoped persisted Domain.config_json, the correct authoritative category list for normal ingestion. The first classification may create a category. Validation of the domain list does not automatically synchronize older engine instances in connector callbacks. verified_at plus verified_outcome=True blocks ordinary confirmed revisions; a false or legacy null outcome is allowed, and the content-creation route has no verified-state guard. An empty edit with the same category can create a successor. A revision token identifies a version; replaying it conflicts rather than returning the original result.
- **Compatibility.** Existing entity field names and the bare-array pending contract survive. Tightened length/category/range checks intentionally convert previously accepted input to 422. Creation races return 409 on the guarded paths. Error messages changed and indexed batch duplicates still return 422 versus 409 for single-ingest conflicts. New webhook writers need event_id and a zoned occurred_at; existing subscriptions need no invented receipt to migrate. The correct rollout order is schema first, then application, then updated ops/test clients. Unique-index prerequisites and historical ownership need reconciliation.
- **Operator evidence.** The batch fix preserves debugging information, but full SQL arguments are unnecessary to distinguish unique violations from other DB errors. Use constraint/error class and an opaque correlation ID. A broad IntegrityError catch cannot establish that all integrity failures are the anticipated race. Verified-incorrect correction needs a substantive change, provenance, a clear authorization rule and a policy for previous learning; a browser-only read-only state cannot enforce any of these.
